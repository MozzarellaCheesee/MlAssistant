# Обработчики намерений

Справочник по пакету `app/application/handlers/`. Каждый обработчик выполняет одно намерение (intent), которое разобрала языковая модель. Причины решений взяты из комментариев в коде и из раздела «Решения и причины» в `README.md`.

## 1. Обзор

### 1.1. Контракт обработчика

Протокол описан в `app/application/handlers/__init__.py:6`:

```python
class Handler(Protocol):
    def handle(self, intent, ctx: TurnContext) -> Result | Question: ...
```

Обработчик получает разобранное намерение и контекст хода. Он возвращает одно из двух:

- `Result` (`app/application/results.py:9`): действие выполнено или дан окончательный ответ. Поля: `text` (ответ), `items` (записи для показа), `referenced_ids` (id записей, на которые можно сослаться словом «её»).
- `Question` (`app/application/results.py:16`): не хватает данных или нужно подтверждение. Поля: `text`, `awaiting` (`slot`, `confirm` или `choose`), `slot` (какое поле спрашиваем: `time`, `date`, `title`, `target`, `recurrence`, `scope`), `key` (имя подтверждения), `options` (id записей для выбора), `items`, `intent` (намерение, которое сохранить вместо текущего).

`TurnContext` (`app/application/results.py:27`) содержит пять полей:

| Поле | Смысл |
|---|---|
| `user_id` | владелец записей |
| `now` | текущее время из `Clock` с часовым поясом |
| `last_ids` | id записей из прошлых ответов, для ссылки «её» |
| `confirmed` | ключи подтверждений, которые пользователь уже дал (`past`, `conflict`, `create`) |
| `source_text` | исходная фраза пользователя |

Обработчики берут время только из `ctx.now`. Так тесты управляют часами через `Clock` (коммит «time only via Clock»).

### 1.2. Диспетчеризация

`AssistantService` получает словарь `handlers: dict[type, Handler]`. Его собирает `build_handlers(repo, search, calendar)` (`app/application/handlers/registry.py:24`); этот же реестр используют `bootstrap.py` и тесты. `test_architecture.py::test_every_intent_has_a_handler` проверяет, что обработчик есть у каждого варианта `Intent`, кроме `Several`:

| Класс намерения | Обработчик |
|---|---|
| `CreateTask` | `CreateTaskHandler(repo, calendar)` |
| `CreateMeeting` | `CreateMeetingHandler(repo, calendar)` |
| `Unknown` | `UnknownHandler()` |
| `Confirm` | `ConfirmHandler()` |
| `ListItems` | `ListItemsHandler(repo)` |
| `SearchItems` | `SearchItemsHandler(search)` |
| `CompleteItem` | `CompleteItemHandler(repo, search, calendar)` |
| `UpdateItem` | `UpdateItemHandler(repo, search, calendar)` |
| `DeleteItem` | `DeleteItemHandler(repo, search, calendar)` |

Для `Several` обработчика нет. Фразу с несколькими командами `AssistantService._chain` делит и выполняет по очереди (`app/application/assistant.py:165`).

В `_turn` вызов выглядит так: `out = self.handlers[type(intent)].handle(intent, ctx)` (`_run`, `app/application/assistant.py:158`). До него сервис (`_turn`, `assistant.py:93`, и `_continue_pending`, `assistant.py:127`):

1. Пытается разобрать ответ без модели через `resolve_reply` (только «да»/«нет» на подтверждение и номер на выбор, `app/application/dialog.py:97`). Иначе зовёт парсер.
2. Заменяет `Confirm` без вопроса-подтверждения на `Unknown` (`assistant.py:111` без открытого вопроса, `assistant.py:132` при вопросе другого вида).
3. Для неясного ответа при открытом вопросе возвращает «Не понял. …» и не вызывает обработчик (`assistant.py:134`).
4. На «да» подставляет сохранённое намерение и добавляет ключ вопроса в `confirmed` (`_answer_confirm`, `assistant.py:148`).
5. На ответ в слот сливает новые поля с сохранённым намерением того же типа и обнуляет `confirmed` (`assistant.py:143`).

### 1.3. Как `Question` становится состоянием диалога

Если обработчик вернул `Question`, сервис выполняет `state.ask(out.intent or intent, out, confirmed)` и сохраняет состояние (`assistant.py:160`). `DialogState.ask` (`app/application/dialog.py:64`) записывает `Pending` с полями: намерение (`model_dump`), текст вопроса, `awaiting`, `slot`, `key`, `options`, `confirmed`. Клиент получает `Reply(out.text, items=out.items, clarify=True)`.

Поле `Question.intent` позволяет сохранить вместо текущего намерения другое. Так делает `resolve_target`: вопрос «Создать задачу?» хранит `CreateTask`, и «да» создаёт задачу (`handlers/target.py:47`).

Если вернулся `Result`, сервис выполняет `state.done(out.referenced_ids)` (`assistant.py:162`): `pending` сбрасывается, а `last_referenced_ids` заменяются новыми id. Если `referenced_ids` пуст, остаются старые (`dialog.py:76`). Поэтому `DeleteItem` для серии возвращает пустые списки: старая ссылка «её» не затирается.

Дальше ответ пользователя попадает в тот же `_turn`:

- `confirm`: «да» повторяет сохранённое намерение с нужным ключом в `confirmed`, «нет» отвечает «Хорошо, отменил.».
- `choose`: номер из списка подставляется в `target.id` сохранённого намерения (`dialog.py:97`).
- `slot`: ответ разбирает модель вместе с черновиком в контексте, поля дополняют намерение.

Причина: словари для свободных ответов («да нет», «не знаю», название, похожее на команду) ошибались. Без модели разбираются только точные «да»/«нет» и номер (README, раздел «Диалог»).

### 1.4. Форма боковой панели

Форма вызывает те же обработчики (`assistant.py:223`). Контекст формы: `confirmed = {"past", "conflict"}`, `last_ids = []`, `source_text = ""`. Любой `Question` форма превращает в `FormError`. Причина: человек сам выбрал дату и время, и вопросы про прошлое и пересечение излишни. Так проверка времени, поиск и календарь работают одинаково для голоса и формы (README, «Форма в боковой панели»).

## 2. `when.py`: вычисление даты и времени

Файл: `app/application/handlers/when.py`. Здесь код превращает названные пользователем день и время в `datetime`. Модель отдаёт время как сказано, а проверяет его код (README, «Понимание запроса»).

### 2.1. `When`

`app/application/handlers/when.py:10`. Датакласс с полями `starts_at: datetime | None` и `due_date: date | None`. Результат разбора времени. `starts_at` бывает пуст у задачи без времени.

### 2.2. `resolve_when(intent, now, need_time, time_question) -> When | Question`

`when.py:15`. Параметры:

- `intent`: любое намерение с полями `shift_minutes`, `time`, `date`.
- `now`: текущий момент с часовым поясом.
- `need_time`: обязательно ли время (для напоминаний и встреч `True`).
- `time_question`: текст вопроса, если время обязательно, но не названо.

Порядок проверок:

1. `shift_minutes` задан и `time` пуст: `starts_at = now + shift`, секунды и микросекунды обнуляются, `due_date` равен дате результата (строки 15-17). Названное время важнее сдвига (комментарий в коде). Поле `intent.date` в этой ветке не учитывается.
2. `time` задано (строка 18):
   - `parse_hhmm` вернул `None`: `Question("Такого времени нет. Во сколько?", "slot", slot="time")`. Причина: модель молча «исправляла» невозможное время («24:30», «29 часов»), теперь отвечает код (README).
   - День равен `intent.date` или сегодняшнему. Время собирается с `now.tzinfo`.
   - Если даты нет и момент `<= now`, прибавляются сутки к времени и дню (строка 24). Комментарий в коде: «только время: ближайшее будущее».
   - Если дата названа и момент в прошлом, функция возвращает его как есть. Прошлое ловит `is_past` в вызывающем обработчике.
3. Времени нет, `need_time=True`: `Question(time_question, "slot", slot="time")`.
4. Иначе `When(None, intent.date)`. Так создаётся задача без времени, возможно и без даты.

### 2.3. `resolve_series(intent, now, need_time, time_question) -> When | Question`

`when.py:34`. Первое вхождение повторяющейся записи. Вызывает `resolve_when`, вопрос возвращает как есть. Дальше:

1. `d = w.due_date or now.date()`. От этого дня ищется ближайшая подходящая под правило дата: `first_on_or_after(intent.rrule, d)` (`app/domain/recurrence.py:122`, просмотр до 62 дней вперёд).
2. Если `first`, `now.date()` и `day` совпадают, время названо и уже прошло, берётся следующая подходящая дата с завтрашнего дня (строки 41-42). Не завтра, а следующая по правилу.
3. `first is None`: `Question("Не понял, как часто повторять. Например: каждый день, по будням, каждый понедельник.", "slot", slot="recurrence")`.
4. Возврат: `When(datetime.combine(first, t) if t else None, first)`, где `t` берётся из `starts_at`.

Порядок вопросов: сначала время (из `resolve_when`), затем правило повтора. Проверка «в прошлом» к сериям не применяется (README, раздел про повторы).

## 3. `calendar.py`: выгрузка в календарь

Файл: `app/application/handlers/calendar.py`. Функции принимают порт `CalendarSync` (`push(item)`, `remove(item)`) или `None`. Ошибка календаря не отменяет действие над записью: функции возвращают строку-предупреждение, а обработчик дописывает её к ответу.

### 3.1. `_WARN`

`calendar.py:7`. Строка `" " + ERRORS[ErrorCode.CALENDAR_FAILED]`, то есть « Запись сохранена, но в календарь не попала.». Текст берётся из таблицы ошибок, а не дублируется.

### 3.2. `_warn(e: AssistantError) -> str`

`calendar.py:11`. Если `e.detail == "no link"` (календарь не подключён), возвращает `""`: выгружать некуда, это не ошибка. Причина: без этого на каждую встречу приходило «в календарь не попала», хотя ошибки не было (README, «Яндекс Календарь»). В остальных случаях пишет `warning` в лог и возвращает `_WARN`.

### 3.3. `sync_item(cal, repo, item) -> str`

`calendar.py:18`. Выгружает или перезаписывает событие. Возвращает `""` или предупреждение.

1. Выходит с `""`, если `cal is None`, запись имеет вид `TASK` (`ItemKind.TASK`) или у неё нет `starts_at` (строка 19). Задачи и записи без времени не выгружаются.
2. Вызывает `cal.push(item)`. Если вернувшийся `uid` отличается от `item.external_id`, сохраняет его в записи и вызывает `repo.update(item)`.
3. `AssistantError` превращает через `_warn`. Другие исключения не перехватываются.

Повторный вызов для той же записи перезаписывает то же событие (README: перенос и переименование перезаписывают событие).

### 3.4. `unsync_item(cal, item) -> str`

`calendar.py:32`. Удаляет событие. Возвращает `""` при `cal is None` или пустом `item.external_id`. Иначе вызывает `cal.remove(item)`. Ошибки идут через `_warn`. Поле `external_id` функция не очищает.

Пользуются функциями: создание (`sync_item`), перенос и удаление (`sync_item`, `unsync_item`). `CompleteItemHandler` синхронизирует календарь только после исключения вхождения серии (`scope == "one"`); обычная отметка «выполнено» календарь не трогает.

## 4. `target.py`: поиск целевой записи

Файл: `app/application/handlers/target.py`. Общий код для `complete_item`, `update_item` и `delete_item`: какую запись имел в виду пользователь и какое повторение серии.

### 4.1. `NOT_FOUND`

`target.py:12`. `Result("Не нашёл такую запись.")`. Возвращается, когда запись по id не найдена или отменена.

### 4.2. `_pick(items, ctx) -> Item | Question`

`target.py:15`. Одна запись возвращается сразу. Если записей несколько, берутся первые пять и возвращается `Question(format_choice(items, ctx.now), "choose", options=[ids], items=items)`. Текст вопроса: «Какую из них? 1) … 2) …» (`render.py:63`). Номер ответа превращается в `target.id` в `resolve_reply`.

### 4.3. `resolve_target(intent, ctx, repo, search) -> Item | Question | Result`

`target.py:22`. Определяет запись по `intent.target`. `Target` содержит ровно одно из полей `id`, `ref`, `query` (`app/application/intents.py:23`).

1. `target.id`: `repo.get(ctx.user_id, id)`. Если записи нет или статус `CANCELLED`, результат `NOT_FOUND`. Выполненные (`DONE`) записи проходят.
2. `target.ref == "last"` (строка 27): берутся записи из `ctx.last_ids` без повторов, порядок сохраняется (`dict.fromkeys`), отменённые отбрасываются. Если пусто: `Question("О какой записи речь?", "slot", slot="target")`. Иначе `_pick`.
3. Поиск по тексту: `search.search(user_id, target.query, SearchFilters(today, kind, "any", intent.date, intent.date), 5)`. Тип берётся из `intent.kind`, дата из `intent.date` (оба поля сужают поиск).
4. Ничего не найдено:
   - для `delete_item` и `complete_item`: `Question("Такой записи нет. Создать напоминание|задачу «{query}»?", "confirm", key="create", intent=CreateTask(title=query, kind=kind))`. Вид `reminder`, если `intent.kind == "reminder"`, иначе `task`. Причина: модель иногда принимает новое дело за команду удаления. Так фраза не теряется, а лишнее не удаляется (README, «Диалог»). Ответ «да» выполнит сохранённый `CreateTask`;
   - для остальных (`update_item`): `Result("Ничего не нашёл по запросу «{query}».")`.
5. Иначе `_pick(items, ctx)`.

Причина поиска по смыслу: ТЗ требует искать по близким по смыслу запросам (README, «Стек»).

### 4.4. `series_scope(item, scope, ctx) -> date | Question | Result | None`

`target.py:53`. Определяет, к какому повторению серии относится команда. Вызывается только для записей с `rrule`.

1. `near = occurrences(item.rrule, item.day(), today, today + 400 дней, item.exdates)`. Вхождения в ближайшие 400 дней без исключённых.
2. Вхождений нет (строка 56): `None` (работаем со всей серией), а при `scope == "one"` `Result("У этой серии больше нет повторений.")`. Вопрос не задаётся.
3. `scope is None`: `Question("Это повторяющаяся запись ({describe(rrule)}). Изменить только ближайшее повторение ({день} {месяц}) или все?", "slot", slot="scope")`.
4. Иначе `near[0]`, дата ближайшего вхождения. Значение возвращается и для `scope == "one"`, и для `"all"`. Выбор «одно или все» вызывающий код делает сам по `intent.scope`.

Docstring функции говорит «None = whole series», но для `scope == "all"` при непустом `near` она тоже возвращает дату. Поведение вызывающих функций от этого не меняется: они смотрят на `intent.scope`.

Комментарий в строке 66 фиксирует известное ограничение: ближайшим вхождением может оказаться сегодняшнее, уже прошедшее. Запоминание даты вхождения из последнего списка не реализовано.

### 4.5. `resolve_scoped(intent, ctx, repo, search)`

`target.py:71`. Объединяет два шага. Возвращает `(item, d)` или `Question`/`Result`, которые вызывающий отдаёт как есть.

1. `resolve_target`. Если результат не `Item` (проверка `hasattr(item, "kind")`), он возвращается.
2. Для серии: `d = series_scope(item, intent.scope, ctx)`; если это не дата и не `None`, возвращается вопрос или отказ.
3. Результат: `(item, d)`; `d` равно `None` для одиночной записи и для серии без ближайших вхождений.

### 4.6. `dm(d) -> str`

`target.py:84`. Формат «5 ноября» (родительный падеж месяца из `MONTHS_GEN`). Применяется в ответах про повторения.

## 5. Создание

### 5.1. `PAST_Q`

`app/application/handlers/create_task.py:11`. `Question("Это время уже прошло. Сохранить всё равно или назовёте другое время?", "confirm", key="past")`. Константа общая: её импортирует `create_meeting.py`. Ответ «да» добавляет `past` в `confirmed`. Ответ новым временем сбрасывает `confirmed`, и проверка идёт заново (README: «Новое время запускает проверку заново»).

### 5.2. `is_past(w, ctx) -> bool`

`create_task.py:23`. `True`, если `starts_at < ctx.now` или `due_date < ctx.now.date()`. Задача на сегодня без времени прошлой не считается. Принимает `When` или `Item`: нужны только поля `starts_at` и `due_date`. `update_item` проверяет им перенесённую запись и новое напоминание.

### 5.2a. `conflict_q(o, verb="Добавить") -> Question`

`create_task.py:14`. `Question("С {HH:MM} до {HH:MM} уже {название}. {verb} всё равно или назовёте другое время?", "confirm", key="conflict")` по первой пересекающейся встрече `o`. `create_meeting` вызывает её с «Добавить», `update_item` с «Перенести». Один текст на оба обработчика, чтобы формулировки не разъезжались.

### 5.3. `CreateTaskHandler`

`create_task.py:28`. Конструктор: `repo: ItemRepository`, `calendar=None`. Создаёт задачу или напоминание (`intent.kind` равно `task` или `reminder`).

`handle(intent, ctx)`:

1. Нет названия: `Question("Что именно записать?", "slot", slot="title")`.
2. Время. `need_time` равно `True` только для напоминания. Вопрос про время: «Во сколько напомнить?». Для повторяющейся записи (`rrule`) вызывается `resolve_series`, иначе `resolve_when`. Вопрос из них возвращается как есть.
3. Прошлое. Если `rrule` нет, время в прошлом и `past` не в `ctx.confirmed`, возвращается `PAST_Q`. Причина: код не даёт создать запись в прошлом без подтверждения (README, раздел про поток данных).
4. `repo.add(Item(...))` с полями `kind`, `title`, `user_id`, `starts_at`, `due_date`, `rrule`, `source_text`.
5. `sync_item` (в календарь уходят только напоминания со временем: задачи пропускаются).
6. Текст ответа:
   - напоминание с повтором: «Буду напоминать {когда}: {название}.»;
   - напоминание: «Напомню {когда}: {название}.»;
   - задача с датой или сроком: «Задача добавлена: {название}, {когда}.»;
   - задача без срока: «Задача добавлена: {название}.».
   К тексту добавляется предупреждение календаря.
7. `Result(text, [item], [item.id])`.

Особенности: конфликты с другими записями не проверяются. Задача с повтором и временем получает `starts_at`, но в календарь не уходит (вид `TASK`).

### 5.4. `CreateMeetingHandler`

`app/application/handlers/create_meeting.py:15`. Конструктор: `repo`, `calendar=None`. Время обязательно.

`handle(intent, ctx)`:

1. Нет названия: `Question("Что за встреча?", "slot", slot="title")`.
2. Время: `resolve_series` при `rrule`, иначе `resolve_when`, всегда с `need_time=True` и вопросом «На какое время поставить встречу?».
3. Прошлое: как у задачи, `PAST_Q` без `past` в `confirmed`; для серий не проверяется.
4. Длительность: `timedelta(minutes=duration_minutes)` или `None`. `ends_at = starts_at + dur`, если длительность названа.
5. Пересечение: `repo.overlapping_meetings(user_id, starts_at, item.effective_end())` до сохранения. `effective_end()` равен `ends_at`, а без него `starts_at` плюс час для встречи (`app/domain/item.py:44`). Если есть пересечение и `conflict` не в `confirmed`: `conflict_q(o)` («… Добавить всё равно или назовёте другое время?»). В тексте указана первая из пересекающихся встреч. У серии проверяется первое вхождение, существующие серии в проверке участвуют (README).
6. `repo.add`, `sync_item`, `Result("Встреча добавлена: {название}, {когда}." + предупреждение, [item], [item.id])`.

Порядок вопросов: название, время, прошлое, пересечение. Оба подтверждения накапливаются в `confirmed`, поэтому после «да» на прошлое пересечение может быть спрошено отдельно.

## 7. Изменение

### 7.1. `CompleteItemHandler`

`app/application/handlers/complete_item.py:12`. Датакласс с полями `repo`, `search`, `calendar=None`.

1. `resolve_scoped`. Вопрос или отказ возвращаются как есть (вопрос о цели, выбор из списка, «Такой записи нет. Создать …?», вопрос о серии).
2. Серия, `scope == "one"`: дата вхождения добавляется в `item.exdates`, `repo.update`, затем `sync_item` серии (как у `delete_item`). Ответ: «Отметил выполненным повторение {дата}: {название}.» + предупреждение календаря. Статус записи остаётся прежним.
3. Серия, остальные случаи: `status = DONE`, затем `unsync_item` (как у `delete_item` для всей серии): будущие вхождения уходят из календаря. Ответ: «Отметил выполненной всю серию: {название}.» + предупреждение календаря.
4. Одиночная запись: `status = DONE`. Ответ: «Отметил выполненной: {название}.»
5. Во всех случаях `Result(text, [item], [item.id])`.

Одиночная запись остаётся в календаре: встреча прошла, это история. Исключённое вхождение уходит в календарь через `exdates` серии.

### 7.2. `DeleteItemHandler`

`app/application/handlers/delete_item.py:12`. Конструктор: `repo`, `search`, `calendar=None`. Запись не стирается, статус становится `CANCELLED`. Так остаётся история, а «её» пропускает отменённые записи (README).

1. `resolve_scoped`, как у `complete_item`.
2. Серия, `scope == "one"`: дата в `exdates`, `repo.update`, затем `sync_item` (серия перезаписывается в календаре, пропущенное вхождение уходит исключением). Ответ: «Удалил повторение {дата}: {название}.». `Result(text, [], [])`.
3. Серия целиком: `CANCELLED`, затем `unsync_item`. Ответ: «Удалил всю серию: {название}.». `Result(text, [], [])`.
4. Одиночная запись: `CANCELLED`, `unsync_item`. Ответ: «Удалил: {название}.». `Result(text, [], [item.id])`. Комментарий в коде: день удалённой записи нужен следующей команде цепочки. `_chain` берёт день из `last_referenced_ids` (`assistant.py:165`). Для серий список ссылок пуст, прежние ссылки сохраняются.

### 7.3. `UpdateItemHandler`

`app/application/handlers/update_item.py:84`. Датакласс с полями `repo`, `search`, `calendar=None`. Выполняет переименование, перенос, сдвиг, напоминание. Возвращает `Result` или `Question`.

Поля намерения: `target`, `date`, `kind`, `title`, `new_time`, `new_date`, `shift_minutes`, `scope`, `remind`, `delay_minutes`, `delay_days`, `delay_months` (`app/application/intents.py:89`).

`handle` читается как оглавление: каждый шаг — функция модуля или метод с говорящим именем. Порядок шагов:

1. Сдвиг «через N минут». Если `shift_minutes` задан и `new_time` пуст, считается `now + shift` без секунд, затем `new_time = "HH:MM"`, `new_date = дата результата` (`_requested_moment`).
2. Проверка времени. `parse_hhmm(new_time)` вернул `None`: `Question("Такого времени нет. Во сколько?", "slot", slot="time")`. Проверка идёт до поиска записи.
3. Название, похожее на вопрос. Фраза и название приводятся к нижнему регистру, «ё» заменяется на «е». Название считается частью вопроса или команды пользователя, если оно (без пробелов, точек, «?», «!» по краям) входит во фразу и при этом фраза заканчивается на «?» или содержит «напиши», «с кем», «как называется». Тогда `Question("Как назвать запись?", "slot", slot="title")` (строки 24-28). Комментарий в коде: эвристика по ключевым словам, замена на проверку через LLM. Код сам называет её временной.
4. Напоминание без времени. `remind` задан, `new_time` пуст: `Question("Во сколько напомнить?", "slot", slot="time")`.
5. Что менять. `delay = timedelta(days=delay_days, minutes=delay_minutes)`, `months = delay_months`. `moved = bool(new_time or new_date or delay or months)`. Если нет ни названия, ни переноса: `Result("Не понял, что изменить.")`.
6. Цель. `resolve_target` (не `resolve_scoped`: дата вхождения нужна позже). `Question` или `Result` возвращаются как есть.
7. Одинаковое название. Название совпадает с текущим и переноса нет: `Result("Запись уже называется «{название}».")`.
8. Серия (если у записи есть `rrule`, `_pick_occurrence` и `_detached_occurrence`):
   - `series_scope` возвращает вопрос о границе («только ближайшее или все») или отказ: они возвращаются;
   - одно повторение (`occurrence` есть, `scope != "all"`): исходная серия сохраняется в `series`, а `item` заменяется копией (`dataclasses.replace`) на дату вхождения: `id=None`, `rrule=None`, `exdates=[]`, `occurrence=None`, `due_date=occurrence`, `starts_at` и `ends_at` на дату вхождения с прежним временем и длительностью, `source_text` из текущей фразы, `notified_at`, `created_at`, `external_id` сброшены. Копия делается до сдвига, поэтому «на час позже» считается от ближайшего повторения.
9. Ближайшее вхождение всей серии (в `handle`: `shift` и `first_day`). `starts_at` серии — первое вхождение, оно может быть давно в прошлом. Для всей серии `shift` — разница в днях между ближайшим вхождением `occurrence` и первым, `first_day = item.day() + shift`. Для остальных записей `shift` нулевой.
10. Сдвиг от самой записи (`_delayed`). Если задан `delay` или `months`:
   - у записи есть `starts_at`: `moved_to = add_months(starts_at + shift, months) + delay`, `new_time` и `new_date` берутся из `moved_to`;
   - иначе, если есть день: `new_date = add_months(first_day, months) + delay.days` (минуты игнорируются).
   Причина: сдвиг считается от самой записи, а не от сегодня. Раньше «на следующий день» отсчитывалось от сегодня, а «на час позже» давало несуществующее время (README).
11. «Напомни о встрече». `remind` и вид `MEETING` (`_remind_about_meeting`): встреча не меняется. Создаётся отдельная запись `REMINDER` с тем же названием, `due_date = day`, `starts_at = day + new_time`, где `day = new_date or first_day or сегодня`. Напоминание в прошлом без `past` в `confirmed` даёт `PAST_Q`, как при создании. Ответ: «Напомню {когда}: {название}.», `Result(text, [r], [r.id])`, календарь через `sync_item`. Причина: раньше такая фраза переносила саму встречу на 9:00, это нашло финальное ревью (README). Вопрос о границе серии при этом всё равно задаётся на шаге 8, а сама серия не меняется.
12. Вся серия на другой день (в `handle`). `new_date` задан и отличается от `first_day`: `Result("Всю серию на другой день пока не переношу. Могу перенести только ближайшее повторение.")`. Совпадает: `new_date` сбрасывается, меняется только время, день первого вхождения серии остаётся прежним. Так «через полчаса» и «на час позже» для всей серии проходят, даже если серия создана давно.
13. Название (`_rename_and_mark`). Если `intent.title` задан, он записывается в `item.title`.
14. Задача становится напоминанием. `remind` и вид `TASK`: `item.kind = REMINDER`. Комментарий в коде: срабатывают только напоминания, в списке задач запись остаётся видна (README: список «задачи» включает напоминания).
15. Перенос (`moved`, `_reschedule`; проверки ниже — `_check_new_time`). `day = new_date or item.day() or сегодня`. Время: `new_time` или время из `starts_at`.
    - Время известно: новое `datetime` с поясом `ctx.now`. Для не-серии `notified_at` сбрасывается, чтобы напоминание сработало заново. Для встречи с `ends_at` конец сдвигается на ту же разницу. Затем `starts_at` и `due_date` обновляются.
    - Времени нет: меняется только `due_date`.
16. Сохранение (`_save_occurrence` для одного повторения, иначе `_save`).
    - Одно повторение серии (`series` задана): `occurrence` добавляется в `series.exdates`, затем `repo.detach_occurrence(series, item)` одной транзакцией обновляет серию и создаёт отдельную запись: при сбое повторение не теряется. Календарь: `sync_item(series) + sync_item(item)`. Ответ: «Перенёс|Переименовал повторение: {название}, {когда}.» (глагол «Перенёс», если `moved`). `Result(text, [item], [item.id])`.
    - Иначе `repo.update(item)` и `sync_item`. Ответы:
      - серия и `moved`: «Перенёс всю серию: {название}, {когда}.»;
      - `moved` и `remind`: «Напомню {когда}: {название}.»;
      - `moved`: «Перенёс: {название}, {когда}.»;
      - только название: «Переименовал: {название}.».
      К тексту добавляется предупреждение календаря. `Result(text, [item], [item.id])`.

Проверки при переносе (`moved`, до сохранения), ключи те же, что у создания:
- прошлое: запись не серия, `is_past(item, ctx)` и `past` не в `confirmed`: `PAST_Q`;
- пересечение: встреча с временем, `conflict` не в `confirmed`, `repo.overlapping_meetings` даёт встречи, кроме самой записи и переносимого вхождения серии (другие вхождения той же серии участвуют): `conflict_q(other, "Перенести")`. Для всей серии окно проверки сдвигается на `shift`, то есть проверяется ближайшее вхождение. Комментарий в коде: остальные даты серии не сверяются.
Форма подтверждает оба ключа заранее.

Причина отдельной новой записи при переносе одного повторения: «Только ближайшее» заносит дату в `exdates`, а при переносе создаётся обычная запись на новые дату и время. Так же ведёт себя и простая смена названия (README, раздел про повторы).

Исключение формы: `update_from_form` сам правит запись на месте, когда меняются вид, время снимается или меняется длительность, потому что `UpdateItem` этого не умеет. Раньше форма создавала новую запись и удаляла старую, и «её» в чате указывало на удалённую (README; код в `app/application/assistant.py:247`).
